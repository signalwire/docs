Messaging SWML is the flavor of SWML used to handle **inbound SMS, MMS, WhatsApp, and RCS
messages**. When a message arrives on a phone number, WhatsApp number, or RCS agent configured with
a SWML message handler, SignalWire fetches and processes the SWML document, optionally sending an
outbound reply on the same channel.

For handling voice calls, see the [Calling SWML overview](/docs/swml/reference/calling).

## Document structure

A Messaging SWML document follows the standard
[SWML document structure](/docs/swml#document-structure) — a top-level `sections` map with
`sections.main` as the entry point. Each section contains an array of
[messaging methods](#methods) that run sequentially. A document can execute up to **100 method
steps** per inbound message; once that ceiling is hit, execution stops.

## Webhook and variable payload [#webhook-payload]

When SignalWire fetches a Messaging SWML document from a URL, it sends the
[inbound message webhook payload](/docs/apis/rest/webhooks/inbound-message-webhook)
to your server in the request body. The request method depends on what triggered the fetch:

- The initial fetch, when the message arrives, uses the request method set on the
  [SWML Webhook](/docs/apis/rest/swml-webhook/create-swml-webhook) assigned to the phone number:
  `primary_request_method` for its primary URL, or `fallback_request_method` when SignalWire falls
  back to its fallback URL. Both default to `POST`.
- A fetch triggered by a [`transfer`](/docs/swml/reference/messaging/transfer) step uses
  `transfer.method` (`POST` by default).
- A fetch triggered by an [`execute`](/docs/swml/reference/messaging/execute) step always uses
  `POST`.

Your server must respond with a valid SWML document using one of these content types:
`application/json`, `application/yaml`, or `text/x-yaml`.

Inside the executing document, the same `message` and `params` fields are available for `%{...}`
variable expansion (for example, `%{message.from}`). As the script runs, methods also set runtime
variables such as `request_result`, which you read the same way (for example,
`%{request_result}`). Those values are not in the initial inbound payload. On fetches triggered by
`transfer` or `execute`, the current values are sent to your server in the payload's `vars` field.

<ParamField path="message" type="object" toc={true}>
  The inbound message that triggered the SWML document.
</ParamField>

<Indent>

  <ParamField path="message.message_id" type="string" toc={true}>
    Unique identifier for the inbound message segment.
  </ParamField>

  <ParamField path="message.project_id" type="string" toc={true}>
    The Project ID this message belongs to.
  </ParamField>

  <ParamField path="message.space_id" type="string" toc={true}>
    The Space ID this message belongs to.
  </ParamField>

  <ParamField path="message.direction" type="string" toc={true}>
    The direction of the message. Always `inbound` for messages that trigger a Messaging SWML document.
  </ParamField>

  <ParamField path="message.type" type="string" toc={true}>
    The channel the message arrived on. Possible values: `sms`, `mms`, `whatsapp`, `rcs`.
  </ParamField>

  <ParamField path="message.from" type="string" toc={true}>
    Sender phone number. In E.164 format for SMS, MMS, and RCS. For WhatsApp, the number as
    WhatsApp reports it: country code and number with no leading `+`, for example `15551231234`.
  </ParamField>

  <ParamField path="message.to" type="string" toc={true}>
    The number or agent that received the message: your phone number in E.164 format for SMS and
    MMS, your WhatsApp number prefixed with `whatsapp:` (for example `whatsapp:+15553214321`), or
    your RCS agent's ID.
  </ParamField>

  <ParamField path="message.body" type="string" toc={true}>
    The text content of the inbound message. For a WhatsApp reply button tap or list selection,
    the ID of the button or list row the customer chose. `null` for WhatsApp media, location, and
    contact messages, and for media-only MMS without a text body.
  </ParamField>

  <ParamField path="message.media" type="object[]" toc={true}>
    Media attachments on the inbound message. Empty array when no media is attached. Always empty
    for WhatsApp, which reports media in `message.whatsapp_context` instead.
  </ParamField>

  <Indent>

    <ParamField path="message.media[].url" type="string" toc={true}>
      URL where the media file is stored.
    </ParamField>

    <ParamField path="message.media[].content_type" type="string" toc={true}>
      MIME type of the media file (e.g., `image/jpeg`, `image/png`).
    </ParamField>

    <ParamField path="message.media[].size" type="integer" toc={true}>
      Size of the media file in bytes.
    </ParamField>

  </Indent>

  <ParamField path="message.segments" type="integer" toc={true}>
    Number of segments the inbound message was split into. Always `1` for WhatsApp.
  </ParamField>

  <ParamField path="message.timestamp" type="string" toc={true}>
    ISO 8601 timestamp of when the inbound message was received.
  </ParamField>

  <ParamField path="message.message_type" type="string" toc={true}>
    WhatsApp and RCS messages only. For WhatsApp, the kind of message the customer sent:
    `whatsapp_image`, `whatsapp_video`, `whatsapp_audio`, `whatsapp_document`, `whatsapp_sticker`,
    `whatsapp_location`, `whatsapp_contacts`, `whatsapp_interactive_button` (a reply button tap),
    or `whatsapp_interactive_list` (a list selection). `null` for a text message. Always `null`
    for RCS.
  </ParamField>

  <ParamField path="message.tag" type="string" toc={true}>
    WhatsApp messages only. For a reply button tap or list selection, the title of the button or
    list row the customer chose. `null` otherwise.
  </ParamField>

  <ParamField path="message.whatsapp_context" type="string | object" toc={true}>
    WhatsApp messages only. Its form depends on what the customer sent:

    - Text message: the string `default`.
    - Reply button tap or list selection: the ID of the WhatsApp message that carried the button
      or list, or `null` when WhatsApp doesn't provide it.
    - Image, video, audio, document, or sticker: an object with `type`, `media_id`, `mime_type`,
      `sha256`, and `url`. A document also has `filename`, and a sticker has `animated`.
    - Location: an object with `type`, `latitude`, `longitude`, `name`, and `address`, plus
      `context_id` and `context_from` when the location replies to an earlier message.
    - Contacts: an object with `type` and a `contacts` array, each entry holding
      `name_information` and `phones_information`.

    Object fields WhatsApp doesn't provide are omitted. Read nested fields with dot notation, for
    example `%{message.whatsapp_context.url}`.
  </ParamField>

  <ParamField path="message.agent_id" type="string" toc={true}>
    RCS messages only. The ID of the RCS agent that received the message, the same value as
    `message.to`.
  </ParamField>

</Indent>

<ParamField path="params" type="object" toc={true}>
  Parameters passed by the calling [`transfer`](/docs/swml/reference/messaging/transfer) or
  [`execute`](/docs/swml/reference/messaging/execute) step. Empty `{}` on the initial inbound
  fetch. Section-scoped — restored to the caller's value when an `execute` returns.
</ParamField>

<ParamField path="vars" type="object" toc={true}>
  Runtime variable scope, populated by methods as the script executes. **Not part of the
  initial inbound payload** — values appear here only after a method that sets them has run.
  The current variables are delivered as a top-level `vars` field on the webhook payload of
  fetches triggered by `transfer` or `execute`. Inside the executing document, read them without
  the `vars.` prefix, for example `%{request_result}`.

  The standard runtime entries are listed below. Methods may also write additional keys; see
  each method's reference page for what it sets.
</ParamField>

<Indent>

  <ParamField path="vars.reply_result" type="string" toc={true}>
    Result of the most recent [`reply`](/docs/swml/reference/messaging/reply) step. Set after
    the step completes. Possible values: `queued`, `failed`.
  </ParamField>

  <ParamField path="vars.reply_message_id" type="string" toc={true}>
    Message segment ID of the most recent successful `reply`. Set after the step completes.
  </ParamField>

  <ParamField path="vars.request_result" type="string" toc={true}>
    Result of the most recent [`request`](/docs/swml/reference/messaging/request) step. Set
    after the step completes. Possible values: `success`, `failed`, `timeout`, `limit_exceeded`.
  </ParamField>

  <ParamField path="vars.request_response" type="object" toc={true}>
    Parsed JSON response from the most recent `request` that saved one. Set when
    `save_variables: true` was set on the `request` step and the URL returned a 2xx response
    whose body is a JSON object. Access nested fields with dot
    notation, e.g., `%{request_response.field_name}`.
  </ParamField>

  <ParamField path="vars.request_response_code" type="string" toc={true}>
    HTTP response code, as a string such as `"200"`, from the most recent `request` that received
    a response.
  </ParamField>

  <ParamField path="vars.request_response_body" type="string" toc={true}>
    Response body, stored as a string, from the most recent `request` that received a response.
    Truncated to its first 65,536 characters.
  </ParamField>

</Indent>

See [Variables](/docs/swml/reference/variables) for variable-expansion syntax, deployment-mode
differences, and tips on accessing nested fields and array elements.

## Methods

A method is a single step in a full-mode SWML document — each item in a `sections.<name>` array
invokes one method. Each method's reference page documents its parameters, defaults, and any
output variables it sets. Methods below are grouped by what they do.

### Message handling

Decide what to do with the inbound message — send an outbound reply, or accept it silently.

<CardGroup cols={2}>
  <Card title="reply" href="/docs/swml/reference/messaging/reply">
    Send a message back to the sender of the inbound message, on the channel it arrived on. Use for auto-replies, confirmations, and keyword responses.
  </Card>
  <Card title="receive" href="/docs/swml/reference/messaging/receive">
    Accept the inbound message without sending a reply. Use to acknowledge the message without an outbound response.
  </Card>
</CardGroup>

### Control flow

Direct execution within the document — reuse blocks of logic, repeat steps, choose between
branches, or hand off the message to another section or document.

<CardGroup cols={2}>
  <Card title="execute" href="/docs/swml/reference/messaging/execute">
    Run another section, or a SWML document from a URL or inline, then resume when it finishes. Use to reuse a sequence of steps from more than one place.
  </Card>
  <Card title="return" href="/docs/swml/reference/messaging/return">
    Hand control back to the section that called the current one, optionally passing a value the caller can read.
  </Card>
  <Card title="transfer" href="/docs/swml/reference/messaging/transfer">
    Hand off the rest of message handling to another section, or to a SWML document from a URL or inline. Execution does not come back; the target takes over.
  </Card>
  <Card title="goto" href="/docs/swml/reference/messaging/goto">
    Restart from a named point earlier or later in the current section. Use for retry loops that repeat a step until it succeeds.
  </Card>
  <Card title="label" href="/docs/swml/reference/messaging/label">
    Mark a place in the section that `goto` can jump to. Labels perform no action; they serve as navigation anchors.
  </Card>
  <Card title="switch" href="/docs/swml/reference/messaging/switch">
    Choose what to do next based on a value from the inbound message or a variable. Use for keyword routing — different replies for different inbound message bodies.
  </Card>
</CardGroup>

### External integration

Reach out to your own backend during message handling, so the reply can depend on data only your
systems know.

<CardGroup cols={2}>
  <Card title="request" href="/docs/swml/reference/messaging/request">
    Call an external API while handling the message — for example, to look up a customer record before replying.
  </Card>
</CardGroup>
