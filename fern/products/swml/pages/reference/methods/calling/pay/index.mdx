Enable secure payment processing during voice calls. 
When implemented in your voice application, it manages the entire payment flow — 
collecting card details (or bank account details, with `payment_method: ach-debit`) from the caller via DTMF, then POSTing them to a `payment_connector_url` you host. 
Your server is responsible for charging the payment method through your payment processor (Stripe, Braintree, etc.) and returning the result to SignalWire.

For a walkthrough that builds a payment flow and its connector from start to finish, see the [take payments on a call guide][take-payments].

## **Transaction Types**

The `pay` method supports two primary transaction types: `charges` and `tokenization`.

### Charges

When you need to process a payment right away, use a charge transaction. 
This collects the payment details and processes the transaction in real-time.

<CodeBlocks>
<CodeBlock title="YAML">
```yaml
version: 1.0.0
sections:
  main:
    - pay:
        charge_amount: "25.00"
        payment_connector_url: "https://example.com/process"
```
</CodeBlock>
<CodeBlock title="JSON">
```json
{
  "version": "1.0.0",
  "sections": {
    "main": [
      {
        "pay": {
          "charge_amount": "25.00",
          "payment_connector_url": "https://example.com/process"
        }
      }
    ]
  }
}
```
</CodeBlock>
</CodeBlocks>
Setting any positive value for `charge_amount` initiates a charge transaction.

### Tokenization

Tokenization allows you to securely store payment information for future use. Instead of processing a payment immediately, it generates a secure token that represents the payment method.
To initiate a tokenization transaction, either pass `charge_amount` as `0` or omit the `charge_amount` attribute entirely.
Your payment connector returns the stored payment method's identifier as `token_id`. See [Response format](#response-format).

<Note>
The token is provided and stored by your payment processor and can be used for future transactions without requiring customers
to re-enter their payment details. Note that this behavior may vary depending on the payment processor you are using.
</Note>

<CodeBlocks>
<CodeBlock title="YAML">
```yaml
version: 1.0.0
sections:
  main:
    - pay:
        charge_amount: "0"
        payment_connector_url: "https://example.com/process"
```
</CodeBlock>
<CodeBlock title="JSON">
```json
{
  "version": "1.0.0",
  "sections": {
    "main": [
      {
        "pay": {
          "charge_amount": "0",
          "payment_connector_url": "https://example.com/process"
        }
      }
    ]
  }
}
```
</CodeBlock>
</CodeBlocks>

## `payment_connector_url`

SignalWire sends a `POST` request to the `payment_connector_url` once all required payment information has been collected from the caller.
Your endpoint processes the payment and returns the result.

SignalWire signs this request with your project's [Signing Key](/docs/platform/webhooks#verify-webhook-signature). The `X-SignalWire-Signature` header holds the lowercase hex HMAC-SHA1 of the connector URL, with any credentials removed, followed by the raw request body, and `X-SignalWire-SHA256-Signature` holds the same value computed with HMAC-SHA256.
SignalWire normalizes the URL before signing it: the scheme is lowercased, `.` and `..` path segments are resolved, and a URL without a path gets `/`, so `https://example.com` is signed as `https://example.com/`.
The request doesn't come from a published IP range, so verify the signature and reject any request that doesn't match.
For a second layer, put credentials in the URL, such as `https://payuser:<LONG_RANDOM_SECRET>@pay.example.com/connector`. They are sent as a standard Basic `Authorization` header and aren't part of the signed URL.
A long random token in the URL path works too, and it is part of the signed URL.

<Warning title="The connector URL appears in your call logs">
The full `payment_connector_url`, including any credentials or token in it, is visible in your call logs in the Dashboard.
Use a secret that protects only this endpoint, and rotate it periodically.
</Warning>

### Response format

Your endpoint must respond with JSON.
SignalWire reads `charge_id`, `token_id`, `error_code`, and `error_message` from the response.
A `200` response with no error counts as a success when it carries a non-empty `charge_id`, or, for tokenization, a non-empty `token_id`.

<Tab title="Successful charge">

Return a `200` HTTP status code with:

<ParamField path="charge_id" type="string" toc={true}>
  A unique identifier for the successful transaction.
  It's available as `payment_confirmation_code` in `pay_payment_results`.
</ParamField>

<ParamField path="error_code" type="null" toc={true}>
  Must be `null` for successful transactions.
</ParamField>

<ParamField path="error_message" type="null" toc={true}>
  Must be `null` for successful transactions.
</ParamField>

```json
{
  "charge_id": "ch_123456789",
  "error_code": null,
  "error_message": null
}
```

</Tab>
<Tab title="Successful tokenization">

For tokenization, `charge_amount` is omitted or written with only zeros and at most one decimal point, such as `0` or `0.00`.
Return a `200` HTTP status code with:

<ParamField path="token_id" type="string" toc={true}>
  A unique identifier for the payment method your payment processor stored.
  It's available as `payment_token` in `pay_payment_results`.
  When `charge_amount` is any other value, `token_id` is ignored and the response needs a `charge_id`.
</ParamField>

<ParamField path="error_code" type="null" toc={true}>
  Must be `null` for successful transactions.
</ParamField>

<ParamField path="error_message" type="null" toc={true}>
  Must be `null` for successful transactions.
</ParamField>

```json
{
  "token_id": "tok_123456789",
  "error_code": null,
  "error_message": null
}
```

Don't return a `charge_id` alongside the `token_id`.
A response with a `charge_id` is treated as a charge, and `payment_token` is then the token type instead of your `token_id`.

</Tab>
<Tab title="Failed charge">

Return a non-`200` HTTP status code with:

<ParamField path="charge_id" type="null" toc={true}>
  Must be `null` for failed transactions.
</ParamField>

<ParamField path="error_code" type="string" toc={true}>
  An error code identifying the type of failure.
</ParamField>

<ParamField path="error_message" type="string" toc={true}>
  A human-readable description of the error.
</ParamField>

```json
{
  "charge_id": null,
  "error_code": "insufficient_funds",
  "error_message": "Card has insufficient funds"
}
```

</Tab>
<Tab title="Failed tokenization">

Return a non-`200` HTTP status code with:

<ParamField path="token_id" type="null" toc={true}>
  Must be `null` for failed transactions.
</ParamField>

<ParamField path="error_code" type="string" toc={true}>
  An error code identifying the type of failure.
</ParamField>

<ParamField path="error_message" type="string" toc={true}>
  A human-readable description of the error.
</ParamField>

```json
{
  "token_id": null,
  "error_code": "invalid_card",
  "error_message": "Card validation failed"
}
```

</Tab>
</Tabs>

<Note>
A non-`200` response plays the `payment-failed` prompt.
A `200` response plays the `payment-completed` prompt even when it doesn't count as a success, for example when its body carries an error, so check `pay_result` for the final outcome.
</Note>

## **Variables**

When the payment process completes, the following [variables](/docs/swml/reference/variables) are set in the `vars` scope.
Access them in subsequent SWML instructions using the `${variable}` syntax (e.g., `${pay_result}`).

<ParamField path="pay_result" type="string" toc={true}>
  The overall outcome of the payment process. Possible values:

  - `success` - The payment was successful.
  - `too-many-failed-attempts` - The caller exceeded the `max_attempts` limit.
  - `payment-connector-error` - The payment connector returned an error.
  - `caller-interrupted-with-star` - The caller pressed the `*` key to cancel.
  - `relay-pay-stop` - The payment was stopped via the `STOP` command.
  - `caller-hung-up` - The caller hung up before completing payment.
  - `validation-error` - Card details failed validation.
  - `internal-error` - An internal system error occurred.
  - `failed` - The `pay` method couldn't run or returned no payment results. `pay_payment_results` is cleared.
</ParamField>

<ParamField path="pay_payment_results" type="string" toc={true}>
  Detailed payment results, including card or bank account details, the token type, and any error information, stored as a JSON-encoded string.
  Because the variable holds JSON text rather than an object, dot notation such as `${pay_payment_results.payment_confirmation_code}` doesn't return the fields inside it.
  When decoded, the JSON object has the fields below.
</ParamField>

<Indent>

<ParamField path="pay_payment_results.result" type="string" toc={true}>
  The payment outcome. Same values as `pay_result`, except `failed`.
</ParamField>

<ParamField path="pay_payment_results.payment_token" type="string" toc={true}>
  For a successful tokenization, the `token_id` your payment connector returned. Use it for future transactions through your payment processor.
  Otherwise, the token type requested in `token_type`: `one-time` or `reusable`.
  If the caller hangs up after your payment connector has created the token, the token is still reported, with `pay_result` set to `caller-hung-up`.
</ParamField>

<ParamField path="pay_payment_results.payment_confirmation_code" type="string" toc={true}>
  The `charge_id` your payment connector returned for a successful transaction.
</ParamField>

<ParamField path="pay_payment_results.payment_method" type="string" toc={true}>
  The payment method used: `credit-card` or `ach-debit`.
</ParamField>

<ParamField path="pay_payment_results.payment_card_number" type="string" toc={true}>
  Redacted card number (e.g., `************1234`).
</ParamField>

<ParamField path="pay_payment_results.payment_card_type" type="string" toc={true}>
  Type of card used (e.g., `visa`, `mastercard`, `amex`).
</ParamField>

<ParamField path="pay_payment_results.payment_card_expiration_date" type="string" toc={true}>
  Card expiration date (e.g., `1225` for December 2025).
</ParamField>

<ParamField path="pay_payment_results.payment_card_security_code" type="string" toc={true}>
  Redacted security code (e.g., `***`).
</ParamField>

<ParamField path="pay_payment_results.payment_card_postal_code" type="string" toc={true}>
  Postal code entered by the caller.
</ParamField>

<ParamField path="pay_payment_results.bank_routing_number" type="string" toc={true}>
  The bank routing number the caller entered. Included only for `ach-debit` payments.
</ParamField>

<ParamField path="pay_payment_results.bank_account_number" type="string" toc={true}>
  The bank account number the caller entered, masked so that at most the last two digits are visible. Included only for `ach-debit` payments.
</ParamField>

<ParamField path="pay_payment_results.bank_account_type" type="string" toc={true}>
  The bank account type: `consumer-checking`, `consumer-savings`, or `commercial-checking`. Included only for `ach-debit` payments.
</ParamField>

<ParamField path="pay_payment_results.payment_error" type="string" toc={true}>
  Error description if the payment failed. Empty on success.
</ParamField>

<ParamField path="pay_payment_results.payment_error_code" type="string" toc={true}>
  Error code if the payment failed. Empty on success.
</ParamField>

<ParamField path="pay_payment_results.connector_error" type="object" toc={true}>
  Error details from the payment connector.
  The object is always included; its `code` and `message` are filled in only when your connector's response carried an `error_code` or `error_message`.
</ParamField>

<Indent>

<ParamField path="connector_error.code" type="string" toc={true}>
  Connector-specific error code.
</ParamField>

<ParamField path="connector_error.message" type="string" toc={true}>
  Connector-specific error message.
</ParamField>

</Indent>

</Indent>
