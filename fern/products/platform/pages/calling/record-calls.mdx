SignalWire lets you [make and receive calls][swml-calls] in several ways and across different channels.
You can record the full conversation, or record fragments and utterances to capture a single message.
Recordings can be found in the [**Storage** section](#view-recordings-from-your-dashboard) of your Space dashboard,
or you can fetch and manage them with the [Recordings API][rest-list].

This guide assumes you can already place or answer a call. If you can't yet, the
[making and receiving phone calls][swml-calls] guide is a great starting point for SWML, and [your first agent][sdk-quickstart]
guide for the Server SDKs. The Server SDKs emit SWML internally, so they are generally equivalent in options and behavior.

## Pick the right product for your requirements

Recording is available across every product, but not all functionality is available in all cases.

- [SWML][swml-intro] is the YAML or JSON document your server returns when a call arrives, and it records with [`record_call`][record-call] in the background or [`record`][record] for a single message.
- [Relay][relay-ns], a Server SDK namespace, holds a live connection to a call in progress, where `call.record()` returns an action handle you can pause, resume, stop, or await for the finished file.
- [Agents][agents-ns], a Server SDK namespace, generates the SWML above — either as an AI agent whose tools return `FunctionResult.record_call()`, or as a `SWMLService` that emits the recording verbs directly.
- [REST][rest-api] API can be directly accessed, or through the Server SDK's [`rest` namespace][rest-ns] wrapper.

## Record the whole call

Recording the entire call for compliance or quality assurance is a common requirement. You can start recording with
`call.record` in the Server SDKs or the [`record_call`][record-call] method in SWML. The recording takes place in the background without interrupting 
the flow of the call, and stops automatically when the call ends. You can also
[stop it early](#stop-recording-the-call), or [pause and resume it](#pause-and-resume-recording).

<Tabs>

<Tab title="Python (Relay)">

```python {15-17}
from signalwire.relay import RelayClient

client = RelayClient(
    project="your-project-id",
    token="your-api-token",
    host="your-space.signalwire.com",
    contexts=["default"],
)

@client.on_call
async def handle_call(call):
    await call.answer()
    await call.play([{"type": "tts", "params": {"text": "This call is being recorded."}}])

    action = await call.record(
        audio={"direction": "both", "format": "mp3", "stereo": True}
    )
    await call.connect([[{"type": "phone", "params": {"to_number": "+15551234567"}}]])

    event = await action.wait()
    print(f"Recording saved: {event.url} ({event.duration}s, {event.size} bytes)")

client.run()
```

### Recording options

There are tradeoffs associated with the some of the recording options, mainly between the file size and the quality of information stored.

The `stereo` property should be set to `true` to put the caller on the left channel and the callee on the right. This 
ensures proper separation of the roles but requires more storage space. If set to `false`, both audio streams get irreversibly mixed down to 
mono. Stereo recording is useful for transcription and other processing later on, but mono stores more compactly, and is usually fine
if the end user of the recording is a human listener.

The `format` property can be `wav` or `mp3`. The `wav` format is uncompressed and several times bigger than the `mp3` format, but
also stores very high quality audio. If the goal is for later processing, transcription and high-fidelity usage, `wav` is the better choice.
SWML also accepts `mp4` to record the video call.

The `direction` property can be `speak`, `listen` or `both`. When recording the whole call in the background, both sides get recorded by default. 
But when recording a part of the call, only the speaker side gets recorded.

`record_call` and `record` accept the same `terminators`, timeouts, and `direction`, but the two
recordings don't put them to the same use. A message recording needs `terminators` and
`end_silence_timeout` to know when the caller has finished, while a full call recording normally
leaves both unset, so a keypress or a pause for breath can't end the file early. Recording the
`speak` direction alone is the norm for a voicemail box and unusual on a call recording. Defaults for
these and for `max_length`, `input_sensitivity`, and `beep` are in the [`record_call`][record-call]
and [`record`][record] references.

### Record after the caller agrees

The Server SDK can pass the control to record a call to the AI agent talking to the caller (or the callee).
To do so, give the agent a tool that enables them to start the recording.

<Tabs>

<Tab title="Python (Agents)">

```python {16-22}
from signalwire import AgentBase, FunctionResult

agent = AgentBase(name="recording-agent", route="/agent")
agent.add_language("English", "en-US", "rime.spore")

agent.prompt_add_section(
    "Recording policy",
    body="Say 'This call may be recorded for quality purposes.' and ask the caller "
    "whether they agree. Call start_recording only after they say yes. "
    "If they decline, continue the call without recording.",
)

@agent.tool(name="start_recording", description="Start recording the call once the caller agrees")
def start_recording(args, raw_data):
    return (
        FunctionResult("Recording has started.")
        .record_call(
            control_id="main",
            stereo=True,
            format="mp3",
            status_url="https://example.com/recording-status",
        )
    )

@agent.tool(name="stop_recording", description="Stop recording the call")
def stop_recording(args, raw_data):
    return FunctionResult("Recording has stopped.").stop_record_call(control_id="main")

if __name__ == "__main__":
    agent.run()
```

### Stop recording the call

A background recording ends on hangup without your help. Stop it yourself when you want the file to
cover only part of the call — audio after the stop is never recorded in the first place.

Every surface addresses a running recording by its `control_id`, so whatever started the recording
can be stopped from anywhere: `stop_record_call` in a SWML script, `action.stop()` in a call handler,
or `calling.record.stop` over REST against any live call.

### Pause and resume recording

To pause and resume recording as the call is happening, you need to use the live control of the call that relay offers.
Pausing takes an optional `behavior`. The default, `skip`, leaves the paused span out of the file
entirely; `silence` replaces it with silence, so the recording's timing still lines up with the call.

## Record a single message

A voicemail box needs the opposite behavior: record, and don't go any further until the caller is
done. The recording ends when they stop talking, press the terminator digit, or run out of time, and
only then does the next instruction run.

<Tabs>

<Tab title="Python (Relay)">

```python {5-6}
@client.on_call
async def handle_call(call):
    await call.answer()

    prompt = await call.play([{"type": "tts", "params": {"text": "Leave a message after the beep."}}])
    await prompt.wait()  # play returns as soon as the command is accepted

    action = await call.record(
        audio={"beep": True, "end_silence_timeout": 3, "terminators": "#"}
    )
    event = await action.wait(timeout=180)

    # no_input is terminal too, so a caller who never spoke lands here with no url
    if event.state == "finished" and event.url:
        print(f"Voicemail saved: {event.url} ({event.duration}s)")
    else:
        print(f"No voicemail recorded (state={event.state or 'call gone'})")

    await call.hangup()
```

</Tab>

the finished action. Note the variable name: [`record`][record] sets `record_url`, while
[`record_call`][record-call] sets `record_call_url`.

`record` captures the caller's side only unless you ask for more. The same `format`, `stereo`, and
`direction` properties apply here — see [recording options](#recording-options).

### Stop recording a message

A message recording is meant to stop on its own, and three properties decide when.
`end_silence_timeout` ends it after that many seconds of quiet, so the caller doesn't have to do
anything at all. `terminators` lets them end it with a keypress the moment they're finished.
`max_length` caps the file however the call goes, which stops a bad line from recording an hour of
noise.

In SWML those are the only ways a `record` ends, because the script is waiting on it and there's no
later instruction to run. `record` defaults `terminators` to `#` for that reason, where `record_call`
leaves it unset. The Server SDKs hand you the same recording as a `RecordAction`, so a handler can
also [stop it explicitly](#stop-recording-the-call) without waiting for the caller.

## Get the recording

Recordings from SWML, the Server SDKs, and Call Flow Builder all land in the same place, and one API
covers them: [List][rest-list], [Get][rest-get], and [Delete][rest-delete].

<EndpointRequestSnippet endpoint="GET /api/relay/rest/recordings" />

<EndpointResponseSnippet endpoint="GET /api/relay/rest/recordings" />

Each entry carries what you need to store a reference and account for the file without a second call:
`url`, `duration_in_seconds` and `byte_size`, `stereo` and `track` for how it was captured, `price`,
and a `status` telling you whether the file is ready. A recording that failed has an `error_code`
instead of usable media. [List call recordings][rest-list] has the full field list, and [paging][paging]
covers the `links` object that gets you past the first page.

### Status callback for recording

Set `status_url` on `record` or `record_call` and SignalWire posts a `calling.call.record` event as
the recording changes state. The one to act on is `finished`: its `params.record` object carries the
`url`, `duration`, `size`, and `format`, which is everything you need to file the recording away.

```json
{
  "event_type": "calling.call.record",
  "params": {
    "call_id": "xxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "control_id": "main",
    "state": "finished",
    "record": {
      "url": "https://your-space.signalwire.com/api/v1/recordings/rec-uuid/download",
      "duration": 15.5,
      "size": 248320,
      "format": "mp3"
    }
  }
}
```

The other states are `recording`, `paused`, `no_input`, and `error`. The full payload is under
[status callbacks](/docs/swml/reference/calling/record-call#statuscallbacks), and [webhooks][webhooks]
covers receiving them in general.

## Secure the media

<Warning title="Recording URLs are public by default">
Media URLs contain randomly generated UUIDs, which makes them impractical to guess, 
but they aren't access-gated by default.

Enable [Media URL protection][media-protection] to require your project's API
credentials to access the recordings.
</Warning>

Protection is set per project and per media type, so recordings can be protected independently of
messages and faxes.

## Recording and the law

Consent requirements and retention rules vary by jurisdiction, and some material like card numbers,
government identifiers, and PINs shouldn't be recorded at all. Below are a few resources to help with
compliance. 

- [Compliance][compliance] covers the regulated workloads SignalWire supports such as HIPAA and TCPA among them.
- [Handling sensitive content][redaction] keeps sensitive values out of recordings, transcripts, and an AI agent's context.
- [Record if the caller agrees](#record-if-the-caller-agrees) discloses the recording and asks before starting one.
- [Pause and resume recording](#pause-and-resume-recording) leaves a gap where a card number is read out, rather than capturing it and redacting later.

## Alternatives to recording

Audio recording is expensive to store and difficult to search. In many cases, a transcription or the 
text summary is all you need. In some cases, only the answers or the result of the call needs
to be stored. SignalWire offers several tools for those requirements. You can use these tools as an alternative to 
recording, or in addition to recording. 

| Requirement | Tool | Result|
|---|---|---|
| Structured summary of the call | An AI agent's post-prompt summary | Structured text at your `post_prompt_url` after the call, from the [`ai`][ai-method] method's `post_prompt` property|
| The full text of the call | [`transcribe`][transcribe] | The whole call transcribed in the background, delivered when the call ends |
| Text while the call is still running | [`live_transcribe`][live-transcribe] | Transcription posted to your webhook as the call happens |
| Advice for a human agent mid-call | [`ai_sidecar`][ai-sidecar] | An AI observer on a human-to-human call, streaming events to your application without speaking |

The post-prompt summary is the most powerful, as you can get the exact result of the call in the exact format you require.
The [conversation analytics guide][ai-analytics] covers it in detail.
