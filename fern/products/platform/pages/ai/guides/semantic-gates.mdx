A semantic gate is a yes/no question about the call, such as "Has the caller explicitly asked to
cancel their ride?", that a decision model must answer yes before your AI agent can run a SWAIG
function. When the answer isn't yes, the function doesn't run, and the agent gets a response you
wrote instead.

Bayview Taxi's dispatcher agent, Ada, shows why that matters. She can cancel a booked ride, but a
caller who asks "What happens if I cancel?" hasn't asked her to. A language model can read it that
way and call `cancel_ride` anyway. A line in the prompt makes that less likely, while a gate on
`cancel_ride` holds the function until the decision model is confident the caller asked to cancel.
The same goes for any action you don't want taken on a guess: refunding, sharing account details,
moving money, or anything that needs the caller's explicit consent.

This guide assumes you already have an agent with SWAIG functions. If you don't, start with
[tool calling][tool-calling].

## How a gate works

A gate sits between the agent's decision to call a function and the function itself. When the agent
calls a gated function, the platform holds the call and sends the decision model what it needs to
answer each of the function's questions. The model returns, for each question, the probability that
the answer is yes, and each gate compares that to the threshold you set.

- **Every gate passes:** the function runs as usual. Your webhook is called, or the `data_map` runs.
- **Any gate fails:** the function doesn't run. The agent gets the failing gate's `on_fail` response
  as the function's result, and answers the caller from it.
- **A gate that allows it answers unclear, and none fails:** the function doesn't run, and the agent
  gets that gate's `on_unclear`, which asks the caller again. See
  [Confirm a change before it runs](#confirm-a-change-before-it-runs).

All of a function's gates are checked at once, and a function can have up to eight. When more than
one fails, the first failing gate in your list decides what the agent gets. A check that can't be
completed, because it ran out of time or the agent's arguments were missing or not valid JSON, blocks
the function too.

Each check the decision model answers is billed, whether the function then runs or not. A check that
includes the caller's video frames is billed as an image check rather than a text check.

## Gate a function

Ada's `cancel_ride` function gets one gate. It asks whether the caller explicitly asked to cancel,
and spells out the near miss in `criteria`: asking about cancelling isn't asking to cancel. The
threshold is high because a cancelled ride is hard to undo.

The [Server SDKs][server-sdks] check your gates by the platform's rules when you define the tool,
and raise an error rather than send a function the platform would refuse.

## Write questions the decision model can answer

The decision model reads the question literally and answers only it, so the question does most of
the work. It reads these inputs, under these names, and nothing else:

| Name | What it holds |
|---|---|
| `conversation` | The most recent part of the call, oldest first: the caller's turns, the agent's replies, and what the agent was told to say outside its replies, such as `say` actions and fillers. 20 entries by default, or only what followed a proposal (see [Confirm a change before it runs](#confirm-a-change-before-it-runs)). An agent turn the caller cut off is marked `interrupted`, with what they heard of it, and a caller turn begun over the agent is marked `while_agent_talking`. |
| `semantic_state` | Whatever your application stored in `global_data.semantic_state`, or `{}`. See [Rely on what your application recorded](#rely-on-what-your-application-recorded). |
| `proposed_function` | The function's name, its description, and the arguments the agent is calling it with. |
| `visual_input` | The caller's newest video frames, when a gate asks for them. See [Look at the caller's video](#look-at-the-callers-video). |

### Name the input in backticks

End or anchor each question with the name of the input it's about, in backticks: "Has the caller
explicitly asked to cancel their ride in `conversation`?" The backticks tell the decision model to
look in the input it was handed under that name, rather than read "conversation" as an ordinary
English word.

The names aren't variables. Nothing replaces `` `conversation` `` with the transcript, and the
platform passes the backticks through as written; they're a convention for the decision model. The
only text substituted in a question is a `${...}` variable from `global_data`, expanded when the
check runs. Write it as `${global_data.pickup_address}` or as the bare top-level key,
`${pickup_address}`. `@{...}` functions aren't run.

### Keep each question to one thing

- **Ask one thing per question.** Split "Did the caller confirm the pickup address and the time?"
  into two gates, so each answer is a clean yes or no.
- **Use `criteria` for the near misses.** Say what counts as yes and what counts as no, especially
  where the two sound alike: "asked about cancelling" isn't "asked to cancel".
- **Don't ask the decision model to calculate or compare dates.** Work the answer out in your
  application, store it in `semantic_state`, and ask about that.
- **Keep it short.** A question can be up to 8 KB, but that's a ceiling, not a target. Most good
  questions are one sentence. Each `criteria` value is capped at 2 KB and `on_fail` at 8 KB, measured
  as compact JSON with its keys and quotes; the [`gates` reference][gates-ref] lists every limit.

Thresholds run from just above 0 to 1, and higher is stricter. Start at 0.9 or above for actions
that are hard to undo, then test against real conversations, including the near misses you wrote
into `criteria`, before you settle on a value.

## Rely on what your application recorded

A caller can say "I already confirmed all that". Whether they did is something your application
knows, not something the conversation proves. Gates read `global_data.semantic_state` as
`semantic_state`, and that's where your application records the facts a gate should rely on: a
ride it looked up, an identity it verified, a refund it worked out the caller is eligible for.

When Ada looks up a trip, the handler stores what the booking system says about it. The
`refund_fare` function then carries two gates: one asks about the recorded fact, the other about
the caller's agreement to the amount the agent is about to refund.

Each write of `semantic_state` replaces the whole object, so to change one field, send the whole
state with that field changed. Send `{}` to clear it. The key is matched exactly, so a state written
as `Semantic_State` never reaches the gates. The state lasts for the call, and carries over to later
`ai` methods in the same call while `persist_global_data` is on, which it is by default. If you set
the `swaig_set_global_data` param to `false`, functions can't write `semantic_state` either.

The rest of `global_data` reaches the decision model only through the `${...}` variables your
questions name. A question that names `${account_tier}` puts that value in front of the model, so
name only values your application set.

Keep `semantic_state` to what your application established, never what the caller claimed. For how
`global_data` works more broadly, see [state management][state-management].

## Write the response a blocked call returns

`on_fail` is what the agent gets instead of the function's result. It's shaped like any SWAIG
function result: a `response`, plus optional `action` and `post_process`. The response is required,
because a blocked function must never read as a success to the agent.

The object form splits the result in two. `tool_result` is what the agent sees as the function's
result ("cancel_ride was not run."), and `tool_prompt` is an instruction placed right after it ("Ask
the caller whether they want to cancel the ride."). Realtime (speech-to-speech) agents get the
`tool_prompt` too, right after the tool result.

`on_fail` can carry actions, such as a `set_global_data` that records the attempt. `action` must be
an array, even for a single action. The whole `on_fail`, its response and its actions, is filled in
once when the call is blocked: `${global_data.*}`, `${args.*}` (the arguments the agent called the
function with), and `@{...}` functions are expanded, so a refusal can repeat what your application
stored, such as `${global_data.semantic_state.proposal}`. A value brought in is never expanded
again, and a `SWML` action keeps its own variable handling.

## Confirm a change before it runs

The hardest gate to get right is the one that waits for the caller's yes. A "yes" might answer an
earlier question, come before the read-back finished, or only sound like agreement. Three settings
make a confirmation gate judge the right moment:

- **Judge only the proposal's conversation.** Store the proposal in `semantic_state` and set
  `dialogue` to `proposal` on the gate, or [`semantic_gate_dialogue`][dialogue-ref] for the whole
  agent. The gate then reads only what was said since `semantic_state` last changed, starting at the
  agent's first turn after it: the read-back and the caller's reply. Until the agent has said
  something, that conversation is empty, so a yes is never judged against a read-back that never
  came. Any change to `semantic_state` starts a new proposal, so keep only the proposal there.
- **Let the read-back play in full.** The [`no_barge_next_response`][actions-ref] action holds the
  caller's words until the agent's next spoken reply has played, then delivers them. The gates see
  the read-back as cut where the caller's answer began, so a yes begun before the change was read out
  is judged on what the caller had heard.
- **Ask again when the answer is unclear.** Set `unclear: true` and the decision model can answer
  unclear as well as yes or no. An unclear answer doesn't run the function: the agent gets the gate's
  `on_unclear`, or a built-in result telling it to ask again plainly. Two unclear answers in a row for
  the same proposal ask again; the third counts as a fail.

A three-way gate shares the probability of yes with unclear, so a plain yes comes back lower. Use a
lower threshold there: about 0.6 where a yes/no gate would use 0.8.

### Build the confirmation flow

When a caller asks Ada to move a pickup, `propose_change` records the proposal and moves to a
`confirm` step. In that step, the agent can call `confirm_change`, which carries three gates judged
on the proposal's conversation, or `decline_change` and `note_request` when the caller says no or asks
for something else. `look_up_ride`, `propose_change`, `decline_change`, and `note_request` are
ordinary webhook functions, so only `confirm_change` is defined below.

                  valid_steps: []

                  functions: [confirm_change, decline_change, note_request]

                required: [revision]
              gate_fillers:
                default:

              gates:

                  criteria:
                    "true": Their latest turn answers with a yes, a no, or more than a listening sound, or it began after the agent had finished.
                    "false": Their latest turn is only a listening sound, and it began while the agent was still talking.
                  threshold: 0.8
                  on_fail:

                    if it cut off the read-back.
                  criteria:

                    "false": Their latest answer says no, hesitates, or asks a question or for something else.
                  threshold: 0.8
                  on_fail:
                    response:
                      tool_result: confirm_change was not run. The caller has not said yes to this change.
                      tool_prompt: Read the change back and ask for a plain yes or no.
                    action:
                      - say: "Just to be sure: ${global_data.semantic_state.proposal}. Should I go ahead?"
                - id: read_back

                  criteria:

                    "false": The read-back described a different change, or none was given.
                  threshold: 0.8
                  on_fail:

The `answered` gate stops a listening sound over the read-back from counting as an answer, `agreed`
checks the answer itself, and `read_back` checks that the caller heard this proposal and not an
earlier one. `agreed` repeats the proposal through `${global_data.semantic_state.proposal}`, which is
filled in when the call is blocked.

`propose_change` returns the proposal, holds the read-back from interruption, and moves to the
`confirm` step. Because the proposal is set as of the start of the result's action list, the
read-back that follows is the first turn the gates judge. When the caller revises the proposal while
in `confirm`, return a new `semantic_state` with `change_step: confirm` again: naming the current
step starts it over, so its text reads the new proposal.

### Judge from a point you mark

A proposal starts whenever `semantic_state` changes. When the moment to judge from isn't a change to
your application's state, such as a quote the agent reads out, set a named mark with the
`semantic_gate_mark` action and give the gate `since` with that name. The gate then judges from the
agent's first turn after the mark; until the mark is set, its `dialogue` applies. A `say` anywhere in
the same result comes after the mark, and setting the mark again moves it. Marks last for the whole
call.

```json
{
  "response": "Refund staged.",
  "action": [
    {"say": "To confirm: a refund of $38.60 to the card ending in 4417. Is that right?"},
    {"semantic_gate_mark": "refund_readback"}
  ]
}
```

A function's gates are asked together about one conversation, so `dialogue`, `history`, and `since`
must be the same on every gate of the function, or the function isn't added to the agent.

## Choose what the caller hears during the check

The check takes a moment, and what fills it depends on the function's settings. A gated function's
`wait_file` plays only once its gates pass, so a blocked call never plays it.

| Function settings | During the check | After the gates pass |
|---|---|---|
| Default: `fillers_at_gates` on, no `gate_fillers` | The function's `fillers`, or the agent's general fillers when it has none | They keep playing |
| `gate_fillers` set | One of the `gate_fillers` | The function's own `fillers`, if it has any |
| `fillers_at_gates: false`, no `gate_fillers` | Nothing | The function's `fillers`, or the agent's general fillers when it has none |

With the default, the caller hears the function's fillers even when a gate then blocks it, and on
standard agents those fillers become part of the `conversation` the gates read. So if a function's
fillers announce the action, such as "OK, cancelling your ride now", give it neutral `gate_fillers`
like "Let me check that", as Ada's `cancel_ride` does, or set `fillers_at_gates` to `false`.
Set it for every function at once in [`SWAIG.defaults`][defaults-ref]; a function's own setting wins.
For functions from `includes`, a `fillers_at_gates` in the `defaults` the include returns wins over
`SWAIG.defaults`.

On standard agents, a function with `wait_for_fillers: true` still waits for its fillers. With the
default, they play first and the gates are checked after them, which adds to the wait; `gate_fillers`
are never waited for before the check. With `semantic_gates_enabled: false`, fillers and the wait
file behave as they do for any function.

The Server SDKs take `gate_fillers` as a tool option. They have no dedicated option for
`fillers_at_gates`, so pass it through as an extra function field:

<CodeBlocks>
<CodeBlock title="Server SDK (Python)">
```python
self.define_tool(
    name="cancel_ride",
    # ... description, parameters, handler, and gates as above ...
    fillers={"default": ["OK, cancelling your ride now."]},
    fillers_at_gates=False,  # these fillers announce the action: say them only after a pass
)
```
</CodeBlock>
<CodeBlock title="Server SDK (TypeScript)">
```typescript
agent.defineTool({
  name: 'cancel_ride',
  // ... description, parameters, handler, and gates as above ...
  fillers: { default: ['OK, cancelling your ride now.'] },
  // These fillers announce the action: say them only after a pass
  extraFields: { fillers_at_gates: false },
});
```
</CodeBlock>
<CodeBlock title="SWML">
```yaml
- function: cancel_ride
  # ... description, web_hook_url, parameters, and gates as above ...
  fillers:
    default:
      - OK, cancelling your ride now.
  fillers_at_gates: false
```
</CodeBlock>
</CodeBlocks>

## Look at the caller's video

On a video call, a gate can look at the caller's camera. Set `visual_input` on the gate to the
number of newest frames it should see, up to 5, and name `` `visual_input` `` in the question:

<CodeBlocks>
<CodeBlock title="Server SDK (Python)">
```python
id_gate = SemanticGate(
    "Is the caller holding a photo ID up to the camera in `visual_input`?",
    threshold=0.9,
    on_fail="verify_identity was not run. Ask the caller to hold their ID up to the camera.",
    id="id_shown",
    visual_input=1,
)
```
</CodeBlock>
<CodeBlock title="Server SDK (TypeScript)">
```typescript
const idGate = new SemanticGate(
  'Is the caller holding a photo ID up to the camera in `visual_input`?',
  0.9,
  'verify_identity was not run. Ask the caller to hold their ID up to the camera.',
  { id: 'id_shown', visualInput: 1 },
);
```
</CodeBlock>
<CodeBlock title="SWML">
```yaml
gates:
  - id: id_shown
    question: Is the caller holding a photo ID up to the camera in `visual_input`?
    threshold: 0.9
    visual_input: 1
    on_fail:
      response: verify_identity was not run. Ask the caller to hold their ID up to the camera.
```
</CodeBlock>
</CodeBlocks>

Frames are taken when the check starts, at most one per second and none older than 8 seconds. If
the call has no video frame to show, the gate fails without being asked, so a gate with
`visual_input` always fails when the post-prompt agent calls the function after the call. A
function's own `visual_input` sends frames to your webhook too, taken at the moment its gates were
checked and never later.

On a video call without avatar clips, capturing frames shows the caller a still image, black by
default. Set the
[`video_blank_image`](/docs/swml/reference/calling/ai/params#paramsvideo_blank_image) param to a PNG
URL to show your own image instead.

## Tune or turn off gates for a call

Four [`ai.params`][params-ref] control checking for the whole call:

| Param | Default | What it does |
|---|---|---|
| `semantic_gates_enabled` | `true` | `false` turns checks off, and gated functions run without being checked. A function with an invalid gate is still left out of the agent. |
| `semantic_gate_timeout_ms` | `2500` | How long one check may take, from 500 to 10000 milliseconds. A check that runs out of time blocks the function. |
| `semantic_gate_history` | `20` | How many recent conversation entries the decision model reads, from 0 to 100. A gate's own `history` overrides it. |
| `semantic_gate_dialogue` | `window` | `proposal` makes gates judge only what was said since `semantic_state` last changed. A gate's own `dialogue` overrides it. |

A value outside its range isn't rejected: it's brought to the nearest end of the range.

<CodeBlocks>
<CodeBlock title="Server SDK (Python)">
```python
agent.set_semantic_gates(timeout_ms=3000, history=30)
```
</CodeBlock>
<CodeBlock title="Server SDK (TypeScript)">
```typescript
agent.setSemanticGates({ timeoutMs: 3000, history: 30 });
```
</CodeBlock>
<CodeBlock title="SWML">
```yaml
- ai:
    params:
      semantic_gate_timeout_ms: 3000
      semantic_gate_history: 30
```
</CodeBlock>
</CodeBlocks>

## Check that your gates work

Call your agent and ask about cancelling without asking to cancel ("What happens if I cancel my
ride?"). Ada should answer the question and leave the booking alone. Then ask her to cancel it: the
function should run.

Every checked call records what happened. Its entry in the `swaig_log`, which arrives in the
[post-prompt callback][post-prompt] and the `calling.ai.swaig` event, carries a `semantic_gates`
object: where the check ran (`phase`: `text` for a standard agent, `oart` for a realtime
speech-to-speech agent, or `post` for the post-prompt agent after the call), which conversation was
judged (`dialogue`: `window`, `proposal`, or `since:<mark>`), the `outcome`, whether the function ran
(`dispatched`), and each gate's `confidence` against its `threshold`. A three-way gate also records
its `choice` (`yes`, `no`, or `unclear`), and `unclear_limit` is `true` when a third unclear answer in
a row was turned into a fail.

```json
"semantic_gates": {
  "evaluation_id": "d7b5c0f2-6a1e-4c8b-9f3d-2b7e1a0c5d44",
  "phase": "text",
  "attempts": 1,
  "latency_ms": 212,
  "outcome": "fail",
  "dispatched": false,
  "gates": [
    { "id": "explicit_request", "threshold": 0.95, "confidence": 0.41, "pass": false }
  ]
}
```

If a function runs when it shouldn't, compare its gate's `confidence` to the threshold, and tighten
the question or its `criteria` before raising the threshold. If a function never runs, look at the
`outcome`:

- `fail` means a gate answered under its threshold. Check that the question names the right input,
  and that the conversation or `semantic_state` actually holds what the gate needs.
- `unclear` means a three-way gate found the answer didn't settle the question. It isn't an error:
  the agent asks again. If it happens on clear answers, check the gate's question and lower its
  threshold.
- `timeout` means the check ran out of time. Raise `semantic_gate_timeout_ms`. On the function's
  first timeout in a row, the agent is told to call the function again.
- `invalid_arguments` means the agent's arguments weren't exactly one JSON object: they were
  missing, weren't valid JSON, had text after the object, repeated a key, or held a `\u0000` escape.
- The function is missing from the agent altogether: a gate is invalid, or the function has no
  `description`, so the platform didn't add the function. A `calling.error` event with
  `error_reason` `invalid_semantic_gate` names the function and the broken rule.
- The function runs without being checked, and its record shows no `semantic_gates`: an earlier
  definition of the same name, often one an include returned, has no gates. The first definition
  of a name wins, so the gated one was dropped. No `calling.error` event fires for this.

A check that passes records `pass`, and one that runs while gates are turned off records `disabled`;
the function runs only on those two. The [post-prompt callback reference][post-prompt] lists every
`outcome`, including the rarer `provider_error`, `invalid_response`, `config_error`, and `aborted`.

Any outcome other than a pass, a fail, or gates turned off also fires a `calling.error` event. The
post-prompt callback adds `semantic_gates_blocked`, the functions the post-prompt agent was blocked
from running, and a `semantic_gates` tally for the whole call.
